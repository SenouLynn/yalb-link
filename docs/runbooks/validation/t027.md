# T-027 Plane 4.6.x QuadPlane target acceptance profile

This runbook records what is known versus assumed about the operator's real
aircraft, the SITL configuration chosen to approximate it, and the
predeclared tolerances for E2E-01 through E2E-04 in the
[operator usage plan](../../tasks/operator-usage-plan.md). No application
writes or flights were performed; this card is a profile and setup, not a
hardware acceptance run.

## Real-hardware facts versus assumptions

Observed/reported (from the operator, not independently verified against the
physical controller):

- Firmware: ArduPilot **Plane 4.6.x** ("not 4.7").
- Board: **MicoAir H743 v1**.
- Frame: **tricopter QuadPlane** (VTOL lift motors plus forward flight surfaces
  on a fixed-wing airframe).

Gaps that only the physical controller or operator can close — do not treat
any SITL run as evidence for these:

- Exact firmware **patch/build** within the 4.6.x line (this profile pins
  4.6.3 as the closest tagged release available at time of writing; the
  operator's board may be on a different 4.6.x patch, or a custom build).
- Board identity/version as ArduPilot actually reports it (`AUTOPILOT_VERSION`
  `board_version`, vendor ID) — MicoAir H743 v1 firmware target and reported
  values are unconfirmed.
- Host OS and USB driver stack for the laptop that will run the application.
- MicoAir LR900-F/-P radio pair serial settings (baud, air rate, protocol) and
  measured throughput.
- Which peripherals are readable over USB-only power (no flight battery) —
  GPS, compass, airspeed, RC input presence are all unverified in that state.
- Actual `Q_FRAME_CLASS`/`Q_FRAME_TYPE` and motor/servo channel mapping on the
  real airframe (this profile's SITL parameters are ArduPilot's stock
  `quadplane-tri` test values, not the operator's tuned configuration).

## SITL configuration chosen, and the mismatch it required fixing

ArduPilot's own SITL tooling (`Tools/autotest/pysim/vehicleinfo.py`) defines a
`quadplane-tri` frame as **two** layered default-parameter files applied in
order — `default_params/quadplane.parm` (base QuadPlane) then
`default_params/quadplane-tri.parm` (tricopter VTOL override) — neither file
alone is a valid frame. Confirmed by reading `Plane-4.6.3` source:
`libraries/AP_HAL_SITL/SITL_cmdline.cpp` registers the `"quadplane"` model
constructor with a prefix match (`strncasecmp`), and
`libraries/SITL/SIM_QuadPlane.cpp` derives the frame class from a `strstr` on
the model string for the `-tri` suffix — so `--model quadplane-tri` reaches
`QuadPlane::create` and correctly configures a tricopter.

`docker/sitl/Dockerfile` previously accepted only a single
`DEFAULT_PARAMS_PATH`, which cannot express this two-file layering. Fixed in
this change: `DEFAULT_PARAMS_PATH` now accepts a space-separated list, copied
into `/sitl/defaults/` at build time with a `/sitl/defaults-manifest` recording
the full comma-joined path list in order; `entrypoint.sh` passes that manifest
straight to `--defaults`, which ArduPilot's `AP_Param::load_defaults_file`
natively accepts as a comma-separated list (confirmed in
`libraries/AP_Param/AP_Param.cpp`). `docker-compose.yml` gained
`ardupilot-sitl-quadplane-tri-4` (profile `target-profile`, sysid 4, host port
5763) using `ARDUPILOT_TAG=Plane-4.6.3`, `WAF_TARGET=plane` and this layered
`DEFAULT_PARAMS_PATH`.

## Verification performed 2026-09-16

```sh
docker compose --profile target-profile up -d --build --wait \
  gcs-backend ardupilot-sitl-quadplane-tri-4
```

- Container log: `Loaded defaults from /sitl/defaults/quadplane.parm,
  /sitl/defaults/quadplane-tri.parm` — confirms the layered-file fix took
  effect (previously only a single file could load).
- pymavlink (`udpclient:host.docker.internal:14551` relay, ad hoc standalone
  boot before wiring into compose) received:
  - `HEARTBEAT`: `type=MAV_TYPE_FIXED_WING`, `autopilot=ARDUPILOTMEGA`,
    `sysid=4`, armed bit clear (boots disarmed).
  - `AUTOPILOT_VERSION`: `flight_sw_version=0x040603ff` → **4.6.3**, matching
    `ARDUPILOT_TAG` exactly.
  - `Q_ENABLE=1`, `Q_FRAME_CLASS=7` (`TRI`), `Q_FRAME_TYPE=1` — confirms the
    tricopter QuadPlane frame class, matching the operator's reported
    configuration at the class level (not the operator's exact tuning).
- Through the real backend/UI pipeline (`docker compose --profile
  target-profile up`, no code changes to the app): `GET /api/events` showed
  `FLEET_EVENT_TYPE_VEHICLE_DISCOVERED` for `systemId=4` with
  `type=MAV_TYPE_FIXED_WING`, `autopilot=MAV_AUTOPILOTMEGA`, followed by
  live `attitude`, `ekfStatusReport` and `globalPosition` telemetry — the
  existing fleet/telemetry pipeline needed no special-casing for this frame.
- A benign SITL startup warning appeared in both the standalone and
  compose-managed boot: `Warning model expected 4 motors and got 3` — this is
  the `QuadPlane` constructor's default X-frame expectation before the `-tri`
  override parameter is applied; it does not affect the resulting frame
  (confirmed by the `Q_FRAME_CLASS=7` readback above) and is not evidence of a
  broken configuration.

This run recreated the already-running `yalb-backend` container (up ~19-23h
alongside `yalb-frontend`/`yalb-sitl-copter-1` from prior work), briefly
dropping any live browser SSE connection and resetting in-memory fleet state.
Persisted recordings were unaffected (separate volume). The added
`ardupilot-sitl-quadplane-tri-4` container was removed after verification;
`yalb-backend`/`yalb-frontend`/`yalb-sitl-copter-1` were left running.

## E2E-01..04 tolerances (defined before execution, per card scope)

These bind the scenario rows already named in the
[operator usage plan](../../tasks/operator-usage-plan.md#intended-end-to-end-scenario-register).
Numbers are chosen from this project's existing conventions (T-019's
comparison/staleness bounds, the connection contract's link states) and from
what the hardware realistically allows; they are commitments to verify
against, not results.

**E2E-01 USB observation**

- Identity freshness: `AUTOPILOT_VERSION`/frame identity resolved and
  displayed within 5 s of controller attachment.
- Telemetry freshness: attitude/heading updates at the controller's live rate;
  UI marks a family stale if no update arrives within 3x its expected message
  interval (matches the connection contract's staleness convention).
- Absence correctness: with no flight battery, GPS fix state, battery
  voltage/remaining and any USB-unpowered sensor must show explicit
  "unavailable"/"no fix", never a stale last-good value presented as current.
- No-mutation: zero `PARAM_SET`, `MISSION_*` write, or command-with-side-effect
  messages observed on the wire during the entire session (verified from a
  raw MAVLink capture, not just UI behavior).
- Recovery: unplug/replug and backend/browser restart each recover correct,
  fresh state within 10 s of the link becoming available again; old
  (pre-disconnect) values must never be redisplayed as fresh on reconnect.

**E2E-02 Parameter inspection**

- Correctness: every parameter name, type and value the UI reports must match
  an independently captured snapshot (MissionPlanner or raw `PARAM_VALUE`
  capture) exactly, including `Q_FRAME_CLASS`/`Q_FRAME_TYPE`/channel mapping.
- Completeness: UI states an explicit count/percentage of parameters received
  versus the controller's advertised total; "complete" is only claimed once
  100% are received with no duplicate IDs.
- Age: each displayed value carries the time of its last `PARAM_VALUE`, not an
  assumed-current label.
- Fault handling: a request that times out or is answered with duplicates
  must not silently merge with, or be presented as equivalent to, a prior
  vehicle's snapshot; reconnect resumes from a known-incomplete state, not a
  false "complete".
- No writes: zero `PARAM_SET` observed for the duration of this scenario.

**E2E-03 Offline powered ground**

- Local load: full UI (assets, no external CDN/font/script fetch) loads with
  no internet route available, per the dependency audit already recorded in
  [T-030](t030.md); imagery absence is shown explicitly, other overlays are
  unaffected.
- Radio-fed freshness: with the real LR900 pair in place of SITL/UDP, position
  and attitude staleness thresholds are the same as E2E-01 (3x expected
  interval), but the interval itself must be re-measured against the radio's
  actual throughput rather than assumed equal to the UDP/SITL rate.
- Recovery: radio interruption and reconnect recover fresh state within 10 s
  of link restoration, matching E2E-01; a browser reload against the same
  live radio session must reach the same live state within 5 s.
- Recording/replay: start/stop and replay work fully offline, matching the
  already-verified T-030 behavior, now against the real radio feed instead of
  SITL/UDP.

**E2E-04 RC field observation**

- Comparison basis: attitude, mode/armed state, position, altitude datum,
  ground speed/climb, battery, GPS/EKF status, home position and mission
  progress are each compared against an independent autopilot log (dataflash
  or MissionPlanner-captured MAVLink) over the same flight, aligned by
  `time_boot_ms`/wall-clock offset established at link start.
- Tolerances: reuse T-019's SITL-established bounds only as an upper bound on
  what to expect (steady-state horizontal position agreement in the low
  single-digit meters, altitude agreement within ~2 m) — report the actual
  measured agreement for this flight rather than assume the SITL bound
  transfers to radio-linked hardware; radio-induced latency/loss may widen it.
- Uncertainty: any telemetry family absent or stale for more than 3x its
  expected interval must show as explicitly uncertain in the UI, never as a
  frozen "last known" value presented as current.
- No commands: zero operator-originated command traffic for the duration;
  flight control is RC-only. This scenario does not exercise arm/disarm or
  navigation command paths.
- Fault coverage: a deliberate post-flight link-loss replay (recording capture
  during the flight, replayed afterward) must reproduce the same instrument
  sequence with no runtime exceptions, matching the replay-verification
  pattern already used in T-019 and T-030.
