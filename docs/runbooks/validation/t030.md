# T-030 Observer startup without internet

This runbook preserves the recorded procedure, results and limitations. Raw
captures for this run are under `docs/temp/evidence/T-030/2026-09-14/`
(screenshots, `innerText` dumps and console logs per step); they are optional
review material and may be pruned per the [artifact policy](../../temp/README.md).

Executed 2026-09-14 with Docker Compose (`gcs-backend` + stationary Copter
4.7.0 SITL, `GCS_RECORDING_ENABLED=true`) and the frontend dev server on the
host (`pnpm dev --port 3001`), driven by headless Chrome over CDP.

## What "no internet" means for this app

A prior read-only investigation (recorded in this card's history) found the
frontend's only runtime network dependency beyond the local backend is basemap
raster tile imagery (`frontend/src/map/tileSource.ts`) — three external hosts
(`server.arcgisonline.com`, `tile.openstreetmap.org`, `tile.opentopomap.org`).
There is no external font, script or CDN dependency; `frontend/index.html`
loads only the bundled `/src/main.tsx`. So blocking those three hosts at the
browser's `Network.setBlockedURLs` — while leaving the page's `localhost`
traffic (the backend API, SSE) untouched — reproduces "internet disconnected,
local stack reachable" for this application without touching host networking.

## Code change

`MapPanel.tsx` and `FleetMap.tsx` had no handling for a failed basemap tile
request: MapLibre reports this as a `map.on('error', {sourceId: 'basemap'})`
event rather than a thrown exception, and nothing listened for it, so a
network-imagery failure was silently a blank/stale ground with no signal to
the operator. Both now show an explicit amber `Imagery unavailable` chip
(`Chip tone="caution"`) in the map legend on that event, cleared on the next
successful style load (basemap switch or retry). Position, track, mission and
fleet-marker overlays are independent GeoJSON sources / DOM markers and were
already unaffected by a failed raster source.

## Procedure and results

1. `GCS_RECORDING_ENABLED=true docker compose up -d --build --wait gcs-backend
   ardupilot-sitl-copter-1` reached healthy status.
2. POST `/api/recordings/start` with name `T-030 offline observer acceptance`
   (recording id 3).
3. **Online control** — default Chrome profile, no blocking. Fleet overview
   and vehicle workspace both rendered the Esri basemap normally
   (`Tiles © Esri` attribution, no unavailable chip). Confirms the later
   offline result is a real effect, not a default app state.
   (`01-online-baseline`, `02-online-vehicle`.)
4. **Offline startup, empty cache** — fresh `--user-data-dir`,
   `--disk-cache-dir=/dev/null`, `Network.setBlockedURLs` on the three tile
   hosts, then `Page.navigate` to the app root. The fleet overview loaded
   fully: live position, altitude, ground speed and link status for vehicle
   1:1, with an explicit `Imagery unavailable` chip and a blank dark ground in
   place of tiles. No console exceptions. (`03-offline-fleet`.)
5. **Offline vehicle workspace** — opened vehicle 1:1 under the same blocked
   session. All instrument groups (link, target state, position, guidance,
   heading, attitude, flight data, raw log families) populated from live
   telemetry; the map showed the same explicit chip alongside the "5 s
   prediction" chip. (`04-offline-vehicle`.)
6. **Offline mission download** — clicked "Download mission" under the same
   blocked session. The mission downloaded (`WAYPOINTS 0.3s`, `#0
   NAV_WAYPOINT`), and the map legend showed `Imagery unavailable` and
   `Commanded mission` together. (`05-offline-mission`.)
7. POST `/api/recordings/stop` flushed 4393 events covering steps 4–6.
8. **Offline replay** — same blocked session, `?source=replay&recording=3`,
   clicked Play. Playback advanced (`0:05 / 2:48`) with battery, GPS fix,
   attitude and track data updating from the recording while the imagery
   chip stayed shown; no imagery fetch was attempted or needed for replay to
   work. (`07-offline-replay-playing`, `08-offline-replay-progressing`.)

## Limitations

- Blocking the three known tile hosts is not a host-level network outage;
  it is the accurate proxy for this app given the dependency audit above; a
  genuinely new external dependency added later would not be caught by this
  block list.
- No radio hardware, USB reconnect or constrained-throughput fault injection
  was exercised — those are out of this card's scope (see the operator usage
  plan's E2E-03 fault coverage; USB/radio interruption applies to hardware
  observation cards, not this browser/SITL-only scenario).
- The imagery-unavailable signal does not currently self-clear when the
  network recovers without a style reload (basemap switch); it is honest
  about the failure it observed, not a live connectivity monitor. Untried:
  whether an operator would want auto-recovery.
- No local/offline tile serving was added; `localTileSource()` already existed
  unused and remains out of scope per the card (tile storage architecture is
  explicitly excluded).

## Reproduce

```sh
GCS_RECORDING_ENABLED=true docker compose up -d --build --wait gcs-backend ardupilot-sitl-copter-1
curl -s -X POST -d '{"name":"..."}' http://localhost:8080/api/recordings/start
(cd frontend && pnpm dev --port 3001 &)
# Fresh profile, empty cache, tile hosts blocked, drive over CDP:
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --headless=new --use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader \
  --remote-debugging-port=9222 --user-data-dir=/tmp/offline-profile \
  --disk-cache-dir=/dev/null about:blank &
# Then Network.enable + Network.setBlockedURLs(["*server.arcgisonline.com/*",
# "*.tile.openstreetmap.org/*", "*.tile.opentopomap.org/*"]) before Page.navigate.
```
