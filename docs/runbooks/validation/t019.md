# Copter motion baseline (T-019)

## Fixed expectations

Use the Compose Copter 4.7.0 `+` model, system/component `1:1`, home
37.7749,-122.4194,10 m MSL, real-time speed. Start disarmed from a fresh
container. Take off to 20 m relative, hold 10 seconds, then command 100 m north
and 100 m east at 5 m/s. Each endpoint must be within 3 m horizontally and 2 m
vertically within 90 seconds. LAND must disarm within 90 seconds. No force arm
or force disarm is used.

Compare displayed five-second prediction endpoints with independently decoded
later positions: straight-leg p95 error <=10 m; turn-phase p95 <=30 m, reported
separately. Browser receipt times and host MAVLink receipt times align captures;
report nearest-sample alignment error. The TCP observation stream is separate
from the backend UDP stream. Compare backend boot timestamps and positions,
MSL/relative altitude and north/east velocity units before relying on UI output.
For matched boot timestamps expect position agreement within 0.02 m, altitude
within 0.002 m and velocity within 0.002 m/s (serialization rounding only).

Withhold GLOBAL_POSITION_INT for 8 seconds using an external simulator rate
command. Require browser position stale by 5.25 seconds after the final
position, and recovery within 2 seconds of restoring 5 Hz. Verify the backend
stream actually loses position; a command ACK is insufficient.

The replay observer clicks Play; speed defaults to 1×. Set duration long enough
for the recording at the chosen speed. Accelerated replay is a rendering and
sequence check, not a wall-time freshness acceptance. The independent DataFlash
comparison aligns POS and ATT with MAVLink boot time (at most 50 ms apart),
reporting actual alignment and field differences rather than treating asynchronous
samples as identical.

After collecting evidence, restore the ordinary simulator link with
`GCS_RECORDING_ENABLED=true docker compose up -d --force-recreate ardupilot-sitl-copter-1`,
or stop the task's containers if no live stack is needed. The relay exits with
the driver, so the override's backend feed stops at that point.

The driver deliberately fixes its connection to localhost:5760. Run only
against the isolated Compose simulator. It refuses wrong firmware, identity,
vehicle type, home and initially armed state. It requires the configured relay peer to be present
before rate injection; identity/version checks alone are not a hardware detector. No application command endpoint
is added. A runtime failure is recorded and exits unsuccessfully; if already
armed it makes a bounded best-effort stream restore and LAND request. Inspect
the simulator after any failed run; recreate before retrying.

`received.mavlink` holds parsed received frames; `received.jsonl` adds decoded
fields, identity, host wall/monotonic receipt time and phase. `commands.jsonl`
separates scenario inputs. `phases.jsonl` records phase starts, endpoint errors
and failures. `firmware.json` records AUTOPILOT_VERSION. Browser JSON contains
rendered text and actual map source geometry at roughly 5 Hz, plus runtime
exceptions; screenshots are captured every 15 seconds. CDP samples can be
slower under load: measure actual cadence when judging a deadline. Map source
inspection instruments only the browser's MapLibre addSource method before
opening the vehicle; it does not substitute calculated trajectory data.

Stop the recording, page through `/api/recordings/ID/events`, and retain the
responses in the run folder. Open `http://localhost:3000/?source=replay&recording=ID`
for replay inspection. Replay uses recorded telemetry event timestamps but
browser playback timing; do not align it directly to live wall time. Report
replay differences and simulator-only limits explicitly.

## Actual results

First setup run (recording 4) completed the route and landed, but is not accepted:
observed speed approached 10 m/s and the backend did not lose position. The
corrected driver sends DO_CHANGE_SPEED after entering Guided position control.
[The pinned Guided implementation](https://raw.githubusercontent.com/ArduPilot/ardupilot/Copter-4.7.0/ArduCopter/mode_guided.cpp)
initializes its speed limits when changing submodes. The
[pinned interval handler](https://raw.githubusercontent.com/ArduPilot/ardupilot/Copter-4.7.0/libraries/GCS_MAVLink/GCS_Common.cpp)
applies intervals to the receiving channel; setting param7 did not pause the
other channel. The relay permits a real simulator stream-rate interruption on
the backend channel, while TCP continues to capture ground truth.

The independent autopilot comparison supports frame/unit interpretation under
asynchronous sampling; it is not a sensor accuracy measurement. The trajectory
uses constant turn rate and velocity, so it cannot anticipate future operator
commands or acceleration. The measured steady interval is only 12.2 seconds;
this does not establish longer-flight accuracy, repeated turns, wind robustness,
Plane behavior or hardware equivalence. Binary captures contain actual simulated
autopilot response, not injected attitude/position. Commands are issued by the
external harness; application command endpoints remain untouched.

Seven runner tests pass, covering route scale/direction, silent/unrelated
telemetry timeouts, disconnect propagation, command rejection, speed-command
ordering and relay preconditions. The analyzer exits unsuccessfully if any
numerical gate fails; raw capture directories are not required test fixtures.

### Revised measurement protocol, fixed before run 3

Run 2 whole north-leg prediction p95 was 19.82 m; it **failed** the original
10 m limit. Errors concentrate in acceleration and five-second horizons that
cross the turn command; steady samples were generally below 1 m. Do not count
this failed whole-leg measurement as a passing straight baseline. For the next
run explicitly distinguish commanded northward acceleration, steady flight,
approach and east turn. Start the steady baseline only when measured horizontal
speed reaches 4.5 m/s; end it at 35 m from the north endpoint, leaving roughly
seven seconds before arrival at requested 5 m/s. Retain the original 10 m p95
bound for that baseline and 30 m for the entire east-turn phase. This validates
the constant-speed model within its stated assumptions, not anticipation of
future control inputs. Report full north-leg p95 alongside the narrower result.

Run 2 sampled disappearance at 5.287 seconds; its 200 ms browser sampling cannot
prove the 5.25-second deadline. Run 3 instruments the actual trajectory source
updates with browser wall timestamps, preserving the unchanged deadline.
Raw TCP and UDP messages had different boot timestamps, so exact matching
between those streams yielded zero pairs. Run 3 retains original UDP datagrams
in the relay as well, permitting exact boot-time and unit comparisons with the
backend, while TCP supplies uninterrupted future positions during the fault.


### Replay and remaining observations

Recording 6 replayed all 4,227 events at 4× to its 2:55 endpoint. The 290 browser
samples show the north/east route, 20 m relative altitude, heading near 0° then
90°, bounded 500-point track and prediction removal/restoration at the recorded
position interruption; runtime exceptions: zero. Accelerated replay compresses
the gap in wall time, so only live timing establishes the 5.25/2-second bounds.
Replay begins paused and without live retained state; the observer explicitly
clicks Play. End-of-recording telemetry becomes stale when the recorded relay
shutdown gap is reached.

Run 3's relay closed immediately after TCP reported disarm, before the next UDP
heartbeat. Its replay therefore retains the preceding armed heartbeat at the
end; the independent TCP and autopilot evidence establish actual disarm. The
runner now drains telemetry for three seconds after disarm. A separate disarmed
terminal smoke checks that this drain forwards the final state; no replay claim
is made that the original recording contains a heartbeat it never received.

The UI reported 256 m flown for a raw TCP route length of 200.75 m (acceleration
through settle). During steady northward flight, map track points periodically
step about 0.7 m backward before resuming forward motion. This is a separate
track/distance defect, recorded in T-052; the baseline does not validate the
Flown counter. The source-order cause is an inference to investigate, not a
proven backend decoding failure: UDP/backend coordinates matched exactly.
